# Lightning 0.7.3

Seven commits since v0.7.2, and this is the release that makes updating
actually work. 0.7.2 was the first release that could be installed *as* an
update — and doing that for real found both Windows paths broken. It also
found that nothing ever told you an update existed unless you went looking.

Everything below came out of running the client and reporting what was
wrong with it.

## Windows updates now install

The first real upgrade test ran four package types. Fedora's RPM, the
Windows Setup EXE and the AppImage all worked. MSI and portable did not,
for two unrelated reasons.

### MSI: `installer-exit-1619`

`ERROR_INSTALL_PACKAGE_OPEN_FAILED`. The package was fine — a valid OLE2
compound file whose SHA-256 matched the signed manifest. The **path** was
the problem. Qt hands out `/` separators on every platform including
Windows, and `msiexec.exe` has its own argument parser that reads `/` as
the start of a switch, so:

```
msiexec /i C:/Users/.../Lightning.msi /qb    → 1619, nothing installed
msiexec /i C:\Users\...\Lightning.msi /qb    → installs normally
```

Confirmed by hand against the same file. The tell was already in the
source: the *program* path was built with backslashes while the artifact
*argument* was left as Qt produced it.

### Portable: `backup-failed`

This one failed on every machine, every time. `lightning-updater.exe` is
launched from the installation directory and links Qt, so the running image
and the DLLs loaded out of that directory are mapped — and **Windows will
not rename a directory while a file inside it is held**. The swap asked it
to do exactly that.

The installation is now moved aside **entry by entry**, and the new one
moved in the same way, leaving the directory itself in place. Renaming
in-use *files* is permitted on Windows — that is how a running binary gets
replaced — so the entries move even though the directory could not.

That change has a consequence worth stating: Windows will not *delete* a
mapped image either, so the backup directory survives the run that created
it. The old code refused outright if the backup path existed, which would
have let exactly one update succeed and every later one fail. A stale
backup directory is now cleared first.

**Neither Windows fix can be verified by updating from 0.7.2**, because the
updater that performs an install is the one already on disk. Windows users
need **one manual install** of 0.7.3; after that, updates should work.

### AppImage came back as the old version

The AppImage upgrade worked, but relaunched into 0.7.1 until it was closed
and started again. `--relaunch` was passed
`QCoreApplication::applicationFilePath()`, which inside an AppImage is the
executable in the *mounted* squashfs — not the `.AppImage` file that was
just replaced. It now relaunches the file it replaced.

## An update tells you it exists

Previously an available update was only discoverable by opening Settings
and pressing a button.

- A **corner card** announces it — deliberately not a modal, because an
  update is never urgent enough to stand between you and your messages.
  "Update" opens the update dialog with the release notes and download
  size; "Not now" dismisses.
- A **badge on the settings gear**: yellow for an update, red when a
  session is unverified. One badge, never two dots, and the security state
  outranks the release.
- Dismissal is **per version**, so silencing one release never hides the
  next. Dismissing the card silences the card, not the fact — the badge
  stays while an update is waiting.
- Both corner prompts (update, unverified session) share one column so they
  cannot draw on top of each other.

**Automatic checks are now on by default**, and switchable off in
Settings → Updates. Nothing about the check itself changed: it is still
anonymous, still at most once a day, still never in the first 30 seconds
after launch, and it still sends only `Lightning/<version>` — no Matrix ID,
homeserver, device ID, token, room data, or tracking identifier of any kind.

## Updates survive the release server being unreachable

Artifact bytes already came from the GitHub mirror, but the manifest was
fetched from the canonical host only — so an outage on the release server
stopped updates being *discovered* rather than merely slowing them down.

The canonical host is still asked first and still decides what exists. Only
when it fails to answer does the client read a mirrored copy of the
manifest pair. This is safe because the parts that make an update
trustworthy do not move: the Ed25519 signature is verified identically
whichever host answered, and the installed-version comparison still refuses
anything that is not strictly newer. The worst a stale or hostile mirror
can achieve is to offer **no** update — never a downgrade, never an
unsigned one.

The mirrored copy lives at a **fixed tag** whose assets the release
pipeline replaces, never a "latest release" URL: that would let GitHub
choose which release answers, which is the thing the no-API rule exists to
prevent.

## Notifications

- **Opening a room no longer fires a notification for every message it
  loads.** Opening a room subscribes it in sliding sync, so the server
  delivers that room's recent history as ordinary live appends — while the
  view is still hydrating, which is exactly when the "you are looking at
  this room" suppression cannot apply, because it requires a settled view.
- **A sender with no avatar gets an initials disc**, the same coloured
  circle every other surface draws, instead of the notification daemon's
  generic document glyph.
- **The Lightning logo appears in the notification itself.** The icon was
  passed only as a theme name, which resolves in an installed deb or rpm
  and nowhere else — a source build, an un-integrated AppImage and a
  Flatpak all fell through to a placeholder.

## Flatpak application ID

The project now has its own domain, and the Flatpak ID moves with it:

```
net.smetonis.Lightning  →  org.lightning_matrix.Lightning
```

Nothing is published on Flathub yet, so this costs a rename now; after
publication it would have cost every user an uninstall and reinstall. If
you installed the 0.7.2 Flatpak **bundle**, it will not be upgraded in
place by this one — remove `net.smetonis.Lightning` and install the new
bundle.

The project home is now <https://lightning-matrix.org>.

## Documentation

The README now carries real per-package installation instructions — deb,
rpm, AppImage, Flatpak (including the runtime it needs), Snap, and a
Windows table covering MSI, Setup EXE and portable with uninstall steps and
checksum verification.

## Validation

CTest **122 passed / 2 failed of 124** on both the Rust and non-Rust trees;
cargo test **111 passed / 0 failed / 4 ignored**. The two failures are the
stale timeline suites documented in the development guide, unchanged by
this release.

New suites: `notification-avatar` and `video-poster-threading`. Each was
checked against the unfixed code rather than merely passing — the MSI
argument assertion, the inode-identity check proving the installation
directory survives the portable swap, and the poster suite, which fails on
the previous tree where the extractor blocked its caller for 891 ms.

Honest status of what is **not** validated: the Windows MSI and portable
fixes cannot be exercised from an already-installed 0.7.2, so they are
code-complete and unverified until someone installs 0.7.3 by hand and
updates from it. Nothing in this release has been tested against Element
for interoperability.

Windows packages remain **unsigned**; the signed update manifest is the
integrity guarantee on every platform.
