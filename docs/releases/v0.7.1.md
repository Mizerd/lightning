# Lightning 0.7.1

Fifteen commits since v0.7.0. The headline is that **Lightning can now
update itself**, verified end to end against a signed manifest — the first
release where installing the next one does not mean downloading a package
by hand. Alongside that: presence indicators, pinned messages, room
administration, room discovery, server-side message search, and a build
that got about eight times faster to work on.

## Secure application updates

Settings → Updates can check for a new release and, for the package types
that allow it, install it. The trust chain is short and every step is
mandatory:

```
public key compiled into Lightning
  -> Ed25519 signature over the exact manifest bytes   (GitLab only)
  -> expected filename, size and SHA-256 of the artifact
  -> those exact bytes fetched from the GitHub mirror, or GitLab if that fails
  -> SHA-256 verified against the signed value
  -> package-specific installation
```

The signature is checked over the raw manifest bytes **before a single
field is read**, using Ed25519 through OpenSSL 3's EVP API — Lightning
implements no cryptography of its own. An invalid signature, an unknown
key id, a wrong hash or size, an unsupported schema, or a URL that is not
HTTPS on an expected host all stop the update, and the interface offers no
way past any of them.

**The manifest names a file. It cannot name a command.** There is no
command, argument or script field anywhere in it, and no code path that
would run one. Every installation strategy is compiled into Lightning and
the updater helper; remote metadata only selects among them.

Per package type:

| Format | Behaviour |
|---|---|
| Windows MSI | Verified MSI handed to Windows Installer (per-user, no elevation) |
| Windows Setup EXE | Verified NSIS installer run in its silent mode |
| Windows portable ZIP | Extracted with strict path checks, layout validated, directory swapped with rollback |
| Linux AppImage | Atomic replace of the running AppImage, previous file restored on failure |
| Linux DEB | Handed to dpkg/APT through PolicyKit — the package manager stays the owner |
| Linux RPM | Handed to dnf5/dnf/rpm-ostree through PolicyKit — likewise |
| Linux Flatpak / Snap | Left to their own ecosystems; Lightning says so and offers the command |

Installation happens in `lightning-updater`, a separate minimal binary
that links Qt Core and zlib and nothing else: no network stack, and none
of Lightning's Matrix, storage or account code. It cannot download
anything, read a token or open a store, because that code is not in it.
Nothing is ever passed through a shell — paths with spaces, quotes or
non-ASCII characters are handled as argument vectors.

Development builds never install anything.

### Downloads come from the GitHub mirror, decisions never do

Update binaries are fetched from the read-only GitHub mirror first, with
GitLab as the fallback, to keep that bandwidth off the project's own
server. GitLab remains the release authority: it alone decides what
version exists and what its bytes must hash to. Lightning makes **no
GitHub API call** and reads no GitHub release metadata — the mirror's URL
is itself part of the signed manifest.

So a compromise of the mirror alone cannot ship an update. Modified bytes
fail the hash. Modified metadata is never read. An extra or newer GitHub
release is invisible. Publishing a trusted update needs the signing key,
which never touches GitHub.

### Privacy

Automatic update checks are **off by default**. A check is an anonymous
HTTPS request for two small public files, carrying only the user agent
`Lightning/<version>` — no Matrix ID, homeserver, device ID, token, room
data, analytics identifier, or updater tracking ID of any kind, because
none is generated. A download additionally reveals the connecting IP to
GitHub, as any file download does. `docs/updates.md` and the privacy
policy state all of this precisely.

## Presence

Online / away / offline dots for other people on unambiguous 1:1 DM rows,
the People list and the member profile popover, with a "last active" line
in the popover. Sliding Sync carries no presence events, so this is a
bounded poll of exactly the users currently on screen. A state Lightning
does not know renders **nothing** rather than a fabricated "offline".
Your own state is published behind Privacy & security → "Share my online
status" (default on; turning it off publishes one final offline).

## Pinned messages

Pin and unpin from the message menu where the room's power levels allow
it, and read the room's pinned list from Room Information. The list *is*
`m.room.pinned_events` — Lightning invents no storage format, and the SDK
does the read-modify-send so a concurrent change cannot be clobbered.
Resolution of pinned events is bounded rather than issuing hundreds of
requests, and a room's pins now appear live instead of after a restart.

## Room administration

- **Member power levels** from the profile popover, offering only changes
  Matrix would actually allow, and never rounding a room's custom numbers
  into a preset: a member at 42 reads "Custom (42)" and stays at 42.
- **Join rule and canonical alias** in Room Information, each gated on the
  room's real required level. Space-restricted rooms are shown honestly
  and left alone rather than silently locked to invite-only.

## Discovery, search, sessions, moderation, drafts

- **Discover / Join Room** — browse and search the room directory, resolve
  `matrix:` and matrix.to links in-app, join, knock, and withdraw a knock.
- **Message history search** through the server's `/search`. E2EE policy is
  explicit: the server cannot search ciphertext, so this covers
  unencrypted rooms only and every surface says so.
- **Per-device sign-out** from Settings → Sessions, with real
  user-interactive auth. OAuth/MAS accounts open the account console
  instead of a password prompt that could not work.
- **Ignore and report** through the SDK's own account data and
  `report_content`.
- **Drafts** — unencrypted rooms persist locally; encrypted rooms are
  memory-only, and a room with unknown encryption state fails closed.

## Fixes

- **Filter chips were invisible in Deep Teal.** The selected chip's fill is
  a tint, but its label used the ink meant for a solid accent fill —
  measured contrast 1.00, i.e. not there at all. The same defect was
  present in Moss Light (1.14) and Lightning Light (1.42) and simply had
  not been reported. Fixed generally rather than per theme, and the
  contrast is now pinned for every theme so it cannot come back.
- Session verification moved to a focused dialog with dismissible prompts.
- Two stale timeline test suites repaired (52 of 63 cases recovered).

## Build

Working on Lightning got dramatically faster. Thirty-two test targets each
recompiled the whole application — 603 of 682 CPU-minutes of a full build,
with one file compiled 43 times. The application is now built once and
linked:

| | Before | After |
|---|---:|---:|
| Full build | 30–50 min | **4 m 54 s** |
| One test target | ~18.6 CPU-min | **20.7 s** |
| CMake configure | 121 s | **58 s** |

A correctness bug fell out of the same work: the Rust build listed 5 of 11
crate sources, so editing six of them silently linked a **stale** library.
`tools/analyze-build.py` reports where build time goes.

## Validation

CTest **110 passed / 2 failed / 112** on both the Rust and non-Rust trees;
the two failures are the stale timeline suites documented in the
development guide, unchanged by this release. Rust: 108 passed / 0 failed.

Honest status of what is **not** yet live-validated: no real MSI, Setup
EXE, portable, AppImage, DEB or RPM upgrade has been performed on a real
machine, and the GitHub mirroring path has been exercised only against a
mock. This release is the first that can be updated *from*, so the first
real end-to-end upgrade will be into 0.7.2.

Windows packages remain **unsigned** — Authenticode signing is prepared
but not active. The signed update manifest is the integrity guarantee
today, on every platform.
