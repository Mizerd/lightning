# Lightning 0.7.2

Twenty-four commits since v0.7.1, almost all of them driven by running the
client and reporting what was wrong with it. This is a polish release: the
headline is that **scrolling a media-heavy room no longer stalls**, from two
separate causes that were measured rather than guessed at. Alongside that:
room search with filters, message forwarding, upgraded-room handling, Space
avatars, and one consistent scrolling feel across the whole application.

It is also the first release that can be installed **as an update** from the
previous one, since 0.7.1 was the first to carry the updater.

## Scrolling no longer stalls on media

Two independent defects were making the timeline hitch, and neither was where
the previous three attempts had looked. Both were found with instrumentation
and are recorded with their measurements, because the scroll-performance area
of this project has a history of plausible fixes that made things worse.

### Every timeline image was decoded at full resolution

`MediaImageProvider` ignored the size QML asked for. Rows request
`sourceSize.width: 640` and leave the height at 0 — the documented Qt idiom for
"keep the aspect ratio" — but the guard read:

```cpp
if (requestedSize.isValid() && !requestedSize.isEmpty())
```

**`QSize::isEmpty()` is true when *either* axis is below 1.** A width-only
request therefore read as "no size requested at all", and every image decoded
at its source resolution into a 348-pixel box, bounded only by the 4096-pixel
safety cap. Measured on a fixture: **3.84 Mpx → 0.27 Mpx, fourteen times fewer
pixels per image**, on a scroll that pulls six to sixteen images per page.

Upscaling is still honoured when a shape is baked into the bitmap — an avatar's
circular mask rasterizes once, and baking it small then displaying it large
aliases the edge.

### The first video in a session froze the UI for a second

Poster extraction for videos with no Matrix thumbnail built its
`QMediaPlayer` and `QVideoSink` **on the GUI thread**. Timed per call:

| Call | Cost on the calling thread |
|---|---:|
| `new QVideoSink` — first in the process | **931 ms** |
| `new QVideoSink` — second | 0.0 ms |
| `setSource` / `play` | 0.0 ms |
| `~QMediaPlayer` | ~68 ms *per video* |
| 66 × `frame.toImage()` | ~232 ms *per video* |

The cost is lazy Qt Multimedia backend initialization — one-time per process,
including a hardware-decoder probe that fails on machines without VAAPI — paid
at the exact moment a video scrolled into view. A heartbeat timer on the GUI
thread measured a **937 ms** stall against a 1 ms idle baseline.

Extraction now runs entirely on a private worker thread. The same measurement
afterwards: **worst stall 1 ms**, with byte-identical poster output. Because
the initialization is process-global, the first inline *playback* is warmed by
the same work and no longer pays it either.

Worth recording: the intuitive explanation was wrong. `frame.toImage()` costs
only 0.24 ms, so "converting every frame is expensive" accounted for none of
the freeze.

### One scrolling feel everywhere

Settings, Home, Room Information, the pickers, the login screen and the
dialogs used Qt's default wheel handling while the timeline used Lightning's
tuned motion. They now share `SmoothWheelArea`.

That change also shipped a defect worth naming, because it says something
about testing: `SmoothWheelArea` resolved its target with `parent as Flickable`,
but a handler declared inside a Flickable attaches to the **content item**, so
the cast produced null — and the wheel handler then swallowed the event while
returning early, leaving nine panes **completely unscrollable**. A contract test
passed throughout, because it scanned QML source for the component's *name*.
The replacement test asserts the resolution at runtime and fails against the old
expression.

## Search inside a room

A search panel with filters for sender, mentions, date, content type and pinned
state, plus global search on Ctrl-Shift-F.

In unencrypted rooms this is the homeserver's own search across full history.
**In an encrypted room the server cannot search ciphertext**, so Lightning
searches the loaded timeline and says which one you are getting rather than
silently returning less. Sender filtering goes through the SDK's
`RoomEventFilter.senders`; the only thing sent anywhere is the search term.

## Forwarding a message

Text, images, video, audio, voice and files can be forwarded from the message
menu into a room picker.

Matrix has no forward primitive and matrix-sdk 0.18 has no helper, so — as in
Element — a forward is the content re-sent as a **new, unrelated event**. Media
is re-uploaded rather than mxc-copied, deliberately: under authenticated media
the target room's members may not be entitled to fetch the source mxc at all,
and an encrypted source's `file` block carries per-event decryption keys that
must not be planted in a room that never negotiated them. The bytes are
re-fetched through the existing media path and re-uploaded, so the SDK
re-encrypts for whatever the target room is.

Filenames and content types are sender-chosen and are re-originated under your
account, so both are sanitized: the filename is reduced to its leaf, and the
type is identified from the file's magic bytes rather than its label.

## Rooms and Spaces

- **Upgraded rooms** are surfaced as a banner offering the successor, never
  followed automatically. The old room stays open and readable, and nothing
  joins, leaves or navigates except by pressing the button. That is a security
  decision as much as a usability one: a room transition discards navigation
  and draft state, and `m.room.tombstone` is state anyone with the power level
  can send — it names the room you would be moved into. Successor and
  predecessor ids come only from the SDK's typed accessors, and the tombstone's
  free-text body never crosses into the interface.
- **A Space can be given an avatar**, not just a name and topic. A Space is a
  Matrix room, so this is `m.room.avatar` through the same setters and the same
  per-state-event permission check that Room Information uses.
- **"Mark as read" works for rooms that are not open.** It had been a silent
  no-op on the Rust backend for every room except the active one: the target
  event was resolved by walking a timeline that only ever holds the open room.
  It now takes the target from the SDK's own `Room::latest_event()` and sends
  the public receipt and `m.fully_read` together.

## Media

- **One shared volume control** for every audio and video player.
- Audio files show their **embedded cover art**, read through Qt Multimedia
  metadata and kept in a bounded memory cache — never written to the disk cache.
- Room Information's **Media and Files** tabs load thumbnails lazily. A video
  with no server thumbnail is no longer downloaded in full just to draw a tile.
- Desktop notifications carry the room or sender's **avatar**, passed as
  in-memory image data with no temporary files.

## Fixes

- The message action bar was clipped on single-line rows. It is now one shared
  instance owned by the timeline, into which rows publish only primitives —
  an earlier attempt that reparented a per-row item into the overlay crashed on
  delegate churn, and is deliberately not repeated.
- Only one action bar shows at a time; a pinned row no longer keeps its bar
  while another row is hovered.
- The timeline scrollbar was drawing on the visual left with a backwards handle,
  because it sat inside the rotated Flickable. It is now an unrotated sibling.
- A binding loop in the action-bar code fired hundreds of times per pagination
  run. It was invisible to the suites that assert on QML warnings, because they
  load the delegate standalone and the loop needs a hover claim to fire at all.
- The room search panel centred its own header and field in encrypted rooms,
  where the results list is hidden; the volume slider's handle rode beside its
  groove rather than in it.

## Validation

CTest **121 passed / 2 failed of 123** on both the Rust and non-Rust trees;
cargo test **111 passed / 0 failed / 4 ignored**. The two failures are the
stale timeline suites documented in the development guide, case-identical
before and after this release's changes and unrelated to it.

New suites in this release include `video-poster-threading`,
`smooth-wheel-area-runtime` and `audio-cover-art-aspect`. Each was checked
against the unfixed code rather than merely passing: the poster suite fails on
the previous tree, where the extractor blocked its caller for 891 ms.

Honest status of what is **not** live-validated. The performance work above is
measured on instrumented harnesses, not confirmed by a user on a real desktop.
Nothing in this release has been exercised against Element for
interoperability, and the room search, forwarding, room-upgrade and Space-avatar
paths have not been run against a real homeserver.

**This is the first release that can be installed as an update.** 0.7.1 was the
first to carry the updater, so no real MSI, Setup EXE, portable, AppImage, DEB
or RPM upgrade has ever been performed — upgrading into 0.7.2 is that first
test. The procedure is in [`docs/updates.md`](../updates.md).

Windows packages remain **unsigned**; Authenticode signing is prepared but not
active. The signed update manifest is the integrity guarantee today, on every
platform.
