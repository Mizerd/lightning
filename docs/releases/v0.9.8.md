# Lightning 0.9.8

The release that actually delivers what 0.9.7 promised, and says plainly where
0.9.7 did not.

## What 0.9.7 promised and could not keep

0.9.7's notes said Lightning "now measures what it is actually sending" and
listed three things. Two of them could not happen in any 0.9.7 package, and
this is the release that makes them true:

* **the microphone's level in the log every few seconds** — the line comes from
  a GStreamer element called `level`, and no 0.9.7 package contained it. On
  Windows the plugin was not in the builder image; in the AppImage it was added
  to the required list one commit *after* the release was cut.
* **a warning in the call header when your microphone produces nothing** — that
  badge is raised from the level readings, so with no element it could never
  appear, whether your microphone was live or dead.

The third promise — *"if the capture never starts, the log says so"* — did work
in 0.9.7 and still does. It sits on a different counter, at the last point
Lightning owns before the network, and has nothing to do with `level`.

Both packages carry the level meter now, and both were checked by running them
rather than by reading the build.

## The microphone could pick the wrong device, or none at all

**Choosing a microphone in Settings could stop capture completely on the
AppImage.** Lightning preferred PipeWire's own capture element, and the version
bundled in the AppImage mishandles the way a device is named there, so the
chain came up with nothing on it: a call that looked perfectly healthy and
carried silence. Lightning now prefers PulseAudio's element, which every
PipeWire desktop also provides.

**And a chosen device could fail to bind at all.** PipeWire's monitor publishes
a node name and a serial, and no `device.name` — the property Lightning matched
on — so a device picked from the list could never be resolved. Both halves are
fixed, and the fix was confirmed against a built package, not a source tree.

## The camera can reach full frame rate on Linux again

**The AppImage** was also missing the JPEG plugin, which is what lets a camera
send its own compressed frames. Without it a USB 2.0 webcam cannot sustain
720p30 and falls back to a lower rate. It ships now, so an AppImage camera takes
the compressed path for the first time.

Windows already had that plugin and is unchanged by this.

## Interoperability, measured

Lightning was tested against other Matrix clients by sending a tone through a
real call and detecting it at the far end, not by watching counters:

* **Sable** — audio both ways, screen share both ways.
* **Element Web**, through Element Call — audio both ways, screen share both
  ways.
* **Lightning to Lightning across platforms**, Windows to Linux — audio both
  ways, screen share both ways.

## Under the hood

The Windows build toolchain moved to Qt 6.11.2, because Fedora withdrew every
6.11.1 package it pinned. Nothing in Lightning asked for a newer Qt.

## Known limitations

* **The Windows package ships GStreamer plugins from `gst-plugins-good`
  without that project's licence text.** It always has; the GStreamer SDK
  Lightning builds against does not carry the file, so it has to be sourced
  from upstream instead of copied. It is recorded rather than quietly fixed.
* **The camera does not display on Windows, and why is not known.** A Windows
  call publishes camera frames correctly — the capture negotiates 1920x1080 at
  30 fps, delivers frames and encodes them — and neither the far end nor
  Lightning's own self-view draws a picture. The renderer is not the cause (the
  session uses Direct3D, not the software fallback) and neither is the
  compressed camera path (it negotiates and delivers). It is being tracked, it
  is not new in this release, and it is not understood yet.
* macOS remains untested for calls.
