# Lightning 0.8.3

A screen-sharing release. The headline is that **a share can now be scaled on
the GPU**, which is the default on every platform, but the more useful change
for most people is probably that **a share carries the computer's audio** and
that the viewer can **turn that audio down without silencing the person**.

## Screen-share audio

A share can now carry what the sharing computer is playing, on Linux and on
Windows. It is a separate, separately encrypted Opus track alongside the
microphone, so the two travel independently and a listener can hear a game and
the person playing it at once.

Live-validated in both directions: sending was confirmed against Element into
an encrypted room, and receiving was confirmed on Element X.

The toggle lives in a menu on the screen-share button rather than in the call
bar, which was a placement fix as much as a feature: on Wayland the portal
picker takes the pointer, and the old position could not be reached at all
once a share had started.

## Per-share volume, and a bug it uncovered

Right-click a share tile for its own volume slider, independent of the
sharer's microphone — turn a game down without turning the person down. It is
offered only when the share actually carries sound, because a control that
cannot move anything is worse than none.

The fix underneath it is the reason this is not only UI. Once a share started
carrying audio, ONE PARTICIPANT COULD PUBLISH TWO AUDIO TRACKS, and both
receive bins named their volume element after the same stream id. The lookup
returns the first match, so setting that person's volume moved whichever bin
GStreamer happened to find and silently left the other alone. Volume elements
are now keyed per track.

## GPU scaling for a share

The convert-and-scale stage of a share can run on the GPU. On Linux the
portal hands over a DMA-BUF the frame is already in, so the import is
zero-copy and only the reduced frame comes back to system memory.

Confirmed working on four environments and two GPU vendors: NixOS from
source and a packaged Windows build (NVIDIA), the Fedora RPM and the Flatpak
(Intel). On Windows a game held 225 of 240 fps while sharing, and the capture
fed the encoder 1:1 where the CPU path at 60 fps had been delivering ~500
frames against ~1500 encoded — `videorate` duplicating each real frame three
times, so two thirds of the encode and encryption was the same picture.

**It falls back to the CPU rather than failing**, and the three ways it can
decline are logged distinctly, because they send you to different places:

* the elements are not in this build — a packaging problem
* the GL stack cannot run here — a driver problem, checked BEFORE a capture
  is opened by building the real chain against a test source and requiring it
  to reach PAUSED
* the description will not build — a caps problem

`LIGHTNING_SHARE_GPU=0` forces the CPU path.

## Share resolution and frame rate

720p / 1080p / 1440p / 4K, and 15 / 30 / 60 fps, chosen from the same menu as
the audio toggle, with both menus kept in sync.

The warnings on those rows are measured rather than guessed. Windows screen
capture sustains 30 fps and does not sustain 60, so 1440p at 60 and 4K at any
rate are marked demanding — and 1080p at any rate is deliberately NOT marked,
because it costs about one frame per second in a running game and a warning on
the setting most people should pick teaches everyone to ignore warnings.

Higher rates (120/144/240) were considered and deliberately not added: the
capture cannot produce them, so selecting one would duplicate each real frame
eight to twelve times and cost eight times the encoding to send the same
pictures.

## Starting a call now tells the room

A MatrixRTC call is a state event, and a state event never appears in a
timeline — so starting one left no trace in the room and no notification for
anyone not already looking. The first participant to join now announces the
call. Later joiners do not, or every arrival would post a row.

## Fixes

* **"Update now" on the update prompt works.** It started the download and
  closed, but every progress indicator and the Install button live in the
  Updates settings section — so the button appeared to do nothing and the
  update could only be completed by finding Settings unaided. It now takes
  you there.
* A share that stops now releases its capture properly; the camera path no
  longer picks up the share's scale settings.
* The screen-share preview works, and the share-quality menu stays open while
  several settings are changed.
* Windows: the GStreamer OpenGL plugin is shipped, and the plugin count
  assertion that guards the payload was corrected.
* AppImage: the OpenGL plugin is bundled, and the validator now asserts it by
  name.

## Known limitations

* **Windows screen capture still costs more than it should.** Capture uses a
  GDI blit of the whole desktop, which forces the desktop compositor out of
  its fast presentation path — measurable as slower window switching, and
  describable as "the display feels like a lower refresh rate" even while the
  frame counter stays high. The fix is DXGI/Windows Graphics Capture, and
  every GStreamer plugin providing it is currently unshippable in this
  toolchain for a C-runtime ABI mismatch. Lower frame rates reduce it
  materially; resolution does not, because the capture is always full-screen.
* **Video does not appear on Element X mobile**, while audio does and video
  works on every other client tested. Not diagnosed.
* **macOS is untested for everything in this release.**
* The five-minute call-dropout fix from 0.8.2 is still NOT live-validated.
