# Lightning 0.7.6

Eleven commits since v0.7.5, and a much smaller round than the one before it —
a follow-up release, driven almost entirely by a real desktop and a real
homeserver rather than by reading code. 0.7.5 shipped profile and Space banners
that had never been used against a live server; this release is largely the
story of what happened when they were.

Plus one new feature: **`@room`**.

## `@room`

Typing `@ro…` now offers a whole-room mention, the way Element does, and it
sends a real `m.mentions.room` — so other clients light up for it properly
rather than seeing a message that merely contains the text.

Two things about it are deliberate:

- **It is offered only where you can actually use it.** The room's own required
  power level for a whole-room notification (`notifications.room`, default 50)
  is asked of the SDK rather than assumed to be "moderator" — rooms are free to
  set it to anything.
- **The message body keeps the literal `@room`.** Every other mention is
  rewritten into a `matrix.to` link; this one is not, because there is no such
  link for "everyone here" and inventing one would put a dead URL in every
  `@room` message ever sent from Lightning.

The suggestion row says what it does — "Notify everyone in this room" — rather
than repeating its own name.

## Banners, against a real server

Three separate reasons the 0.7.5 banners did not work, all found by looking
rather than guessing.

- **The profile endpoint was unreachable.** The homeserver
  (Synapse 1.156.0) implements MSC4133 and answers
  `GET /_matrix/client/v3/profile/<user>/m.banner_url` correctly — verified by
  hand against the live server. Lightning could not reach it. ruma only selects
  that stable path when the server advertises spec version 1.16, and Synapse
  signals a stabilised MSC the way it always has — `uk.tcpip.msc4133.stable` in
  `unstable_features` — while its version list stops at v1.12. Neither gate is
  met, so every read came back "unrecognised" and Lightning reported that the
  homeserver does not support profile banners **about a homeserver that does**.
  The three calls now address the stable path themselves, over the SDK's own
  transport. The *answer* decides what the server supports; nothing is concluded
  from a version number in either direction. No dependency changed.
- **The room banner had a name nobody else reads.** 0.7.5 invented
  `org.lightning_matrix.room_banner`, which was wrong the moment another client
  already had one: Sable writes `page.codeberg.everypizza.room.banner`, in the
  same shape. Lightning writes Sable's name now, so a banner set in one shows up
  in the other. The old name is still **read**, after it, so banners written by
  0.7.5 do not vanish — it is simply never written again.
- **Picking a banner file was broken on Windows.** Both pickers stripped
  `file://` by hand, which turns `file:///C:/pic.png` into `/C:/pic.png` — a
  path with a leading slash before the drive letter. Linux never notices, which
  is why it survived review. The conversion moved to one place in C++ where no
  caller can get it wrong.

## Banners you can actually live with

The Space banner is **cropped by default** now — a fixed 190 px strip, as Sable
renders it, so every Space is the same shape and the rooms below stay where the
eye expects them. Two controls in the banner's corner change that:

- **Expand** shows the whole picture at whatever height its aspect ratio needs.
- **Hide** removes the strip entirely — and has a way back, because a control
  that can only be turned off is a trap.

Both choices are app-wide rather than per-Space: someone who does not want a
400 px picture above every Space does not want to say so once per Space. And the
view controls are *not* behind the power-level gate the edit buttons are — they
change how this client shows the banner, not the banner.

The controls also became legible. They were words painted directly on a
photograph: "Change banner" in outline blue over a bright blue planet, "Remove"
in danger red over black space. A control drawn on an arbitrary picture has no
background to have contrast *with*, so it gets one — a single dark pill built
from the media-chrome tokens the GIF and size badges already use.

## Fixes

- **The composer text sat six pixels low until you clicked it.** Reported three
  times, and chased through padding, insets, the placeholder, the platform style
  and an anchor loop — every one of which was measured and disproved, because
  the test harness kept reporting perfect alignment. It reported that because it
  was not rendering the application's font. With the real font loaded it
  reproduced immediately: Qt's `TextArea`-in-`Flickable` integration parks the
  scroll position at −6, painting the line below the box that holds it. Clicking
  the field is what reset it, which is exactly the "it fixes itself when you
  click it" half of the report.
- **Drop a file, press Enter.** Dropping a file focused the composer's root
  rather than its input, so Return did nothing until you clicked the message box
  — which is the entire point of the affordance.
- **"All" was showing fewer rooms than "People".** Direct messages were being
  scoped by the selected Space, and a DM is not a room in a Space. A DM is now
  never scoped by a Space in any filter, so All is exactly People plus Rooms.
- **The People tab inside a Space was empty by construction** — for the same
  reason, in every Space, always.
- **The empty state stopped answering the wrong question.** "This Space is
  empty / Rooms added to this Space will show up here" appeared under the People
  chip, describing a list nobody was looking at. It is keyed on the filter now.

## Not tested

Live validation not performed for this release: the write half of profile and
Space banners against a homeserver, and their permission gates — the read path
is proven by hand against the real endpoints, the write path is not; `@room`
against a live room, including whether other clients notify for it;
interoperability of Lightning's Sable-named room banner with Sable itself; and
the macOS build beyond `--version` and `--build-info`.

Two reports remain **open and unfixed**, and are not claimed otherwise:

- **Uploads fail from the Windows MSI build**, while the same version installed
  from the Setup EXE or the portable ZIP uploads normally. The payloads are
  byte-identical between the MSI and the EXE, so the difference is in the
  install rather than the application; a mixed or leftover install is the
  current suspicion and it has not been confirmed.
- **Sync can lag well behind Element**, occasionally by around a minute. Not yet
  reproduced or instrumented, and deliberately not guessed at.

Voice and video calls remain unavailable — the signalling and media stack exist
in the codebase but stay disabled, because no answered call has been validated
on a real network.

Windows and macOS packages remain **unsigned**. The signed update manifest is
the integrity guarantee on every platform.
